1 · Vì sao: tách KHUÔN khỏi CHẤT ĐIỀN

Code (main.tf) nên là thứ ổn định; giá trị (IP, cỡ máy, region) đổi hàng ngày. Nhét giá trị vào code = mỗi lần đổi phải sửa code + dễ sửa thiếu (IP nằm ở 1 chỗ SG, mai mốt 5 chỗ). Variable giải quyết cả hai: khai báo cái lỗ, điền giá trị bên ngoài.

2 · Anatomy của variable

variable "my_ip" {
  description = "IP duoc phep SSH vao may"  # hiện khi plan hỏi giá trị
  type        = string                        # string | number | bool | list(string) | map(string)
  # KHÔNG default = bắt buộc người chạy phải cung cấp (plan sẽ DỪNG hỏi)
}

variable "instance_type" {
  type    = string
  default = "t3.micro"   # có default = tùy chọn; người dùng không nói gì thì dùng cái này
}

4 · Output — biến chiều ngược lại

output "public_IP" {
  description = "IP cong khai de truy cap"
  value       = aws_instance.example.public_ip
}
terraform output                  # xem tất cả
terraform output public_IP          # một cái
terraform output -raw public_IP     # không dấu nháy → IP=$(terraform output -raw public_IP)
Đặc tínhÝ nghĩa thực chiến
Output lưu trong state, in ra cuối mỗi applyÁp dụng output mới có thể tạo plan "0 added, 0 changed, 0 destroyed" — apply metadata, không đụng hạ tầng ("You can apply this plan to save these new output values... without changing any real infrastructure")
Output track nguồn của nóNguồn đổi → output đổi theo: ~ public_IP = "..." -> (known after apply) xuất hiện khi resource nguồn sắp stop/start
Terraform không in giá trị output ra giữa plan nếu nó phụ thuộc thứ chưa tạoĐó là lúc bạn gặp (sensitive value) / known after apply ở mục Changes to Outputs

5 · Thí nghiệm đã chạy — và kết luận

A — Refactor không đổi đời: thay 3 hard-code bằng biến với cùng giá trị → plan chỉ ra "Changes to Outputs", không resource nào đổi. Plan sạch (phía infra) là bài test của mọi lần chỉ-dọn-code.
B — TF_VAR test không nhiễm: TF_VAR_instance_type=t3.small terraform plan → ~ instance_type = "t3.micro" -> "t3.small", update in-place (khác key_name = replace). Nhưng kèm chữ ký quen mặt: public_ip -> (known after apply) trong khi id giữ nguyên → AWS không đổi size lúc đang chạy → provider stop → đổi → start, và stop/start thì đổi public IP. Cách đọc: id nguyên + public_ip known-after = "có nhịp stop/start phía sau". Không apply — env var chỉ sống bằng lệnh plan đó.
C — Biến bắt buộc: tắt tfvars đi (mv) → plan dừng tại var.my_ip: Enter a value:. Không phải lỗi — là thiết kế: thiếu nguyên liệu thì hỏi, không tự chế.
Bẫy hoa-thường: bạn đặt variable "my_IP" — Terraform phân biệt chữ hoa/thường; tfvars/env phải khớp tên từng ký tự (my_IP ≠ my_ip). Chuẩn cộng đồng: snake_case thuần, my_ip.

6 · Quiz tự kiểm tra

1. Variable không default, không tfvars, không env → chuyện gì khi chạy plan?Plan dừng và hỏi tương tác "Enter a value". Nếu muốn nó không bao giờ hỏi (CI), cho default hoặc buộc qua tfvars commit sẵn.
2. Vì sao ["var.my_ip/32"] là lỗi nhưng Terraform không báo lỗi?Nó là chuỗi hợp lệ — Terraform không bắt được "ý bạn là khác".plan chỉ báo SG đổi giá trị CIDR (in-place) — đọc plan mới thấy. Cú pháp đúng ≠ ngữ nghĩa đúng.
3. TF_VAR_ip=x plan xong, lệnh plan thường tiếp theo dùng giá trị nào?Giá trị trong default/tfvars — env var chỉ sống bằng tiến trình lệnh đó.
4. Apply chỉ có "Changes to Outputs" thì hạ tầng thay đổi gì?Không gì cả. Output là metadata trong state. Resources: 0/0/0.
5. Đổi instance_type update hay replace? Vì sao public_ip vẫn (known after apply)?Update in-place (cùng id), nhưng AWS yêu cầu stop máy mới đổi được size → provider stop→modify→start → public IP động bị cấp lại.
6. Output công dụng gì ngoài in cho vui?Kết nối với thế giới: script/CI lấy IP bằng terraform output -raw; output của stack này làm input stack khác (terraform_remote_state); description + sensitive=true khi chứa bí mật.
