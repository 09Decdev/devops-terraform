1 · user_data & cloud-init là gì

user_data = đoạn script nhét vào "túi đồ" của instance lúc tạo. Mỗi AMI Linux đều chứa cloud-init — chương trình chạy ngay lúc máy boot lần đầu, đọc túi đồ đó và thực thi script với quyền root.

Vì sao không SSH vào cài tay? Vì máy chủ có thể bị đập và tạo lại bất cứ lúc nào. Script nằm trong main.tf = DNA: mọi máy sinh ra từ code đều tự biết mình phải là web server. Đây là điểm khác biệt giữa "xài server" và "làm chủ server".

2 · Code đã viết

① user_data trong block aws_instance (kèm công tắc)

user_data = <<-EOF
  #!/bin/bash                          # chạy bằng bash
  dnf install -y nginx                 # -y = tự trả lời yes khi cài
  systemctl enable --now nginx        # bật ngay + tự bật mỗi lần reboot
  echo "<h1>...</h1>" > /usr/share/nginx/html/index.html
EOF

# KHÔNG cần sudo — script đã chạy với root qua cloud-init
user_data_replace_on_change = true   # ← công tắc: đổi script = đập máy tạo lại
Khái niệmGiải thích
<<-EOF ... EOFheredoc — "mở khối văn bản tới khi gặp EOF". Dấu - = cho phép thụt lề mà không làm hỏng script.
Plan in thành <<-EOTTerraform tự normalize EOF→EOT khi hiển thị — không phải code bạn sai.
user_data_replace_on_change = trueMặc định false (provider ≥ 5.0): đổi script chỉ cập nhật tại chỗ, máy không bị đập. Bật true = mỗi lần sửa script, máy tạo lại từ đầu để đảm bảo script chạy lại.

ingress {

  cidr_blocks = ["0.0.0.0/0"]   # web PHỤC VỤ THIÊN HẠ — khác SSH!

3 · 5 bài học ngoài kế hoạch (xảy ra thật, nhớ lâu gấp 10)

Bài 3.1 — "Túi khí chỉ bung khi va chạm": công tắc chỉ tác động thay đổi TƯƠNG LAI

Chuyện: thêm user_data_replace_on_change = true → plan chỉ ra ~ update in-place, không replace. Vì lúc đó script không đổi — công tắc mới lắp, chưa có "va chạm" nào. Muốn tạo lại máy NGAY, phải dùng: 
terraform apply -replace=aws_instance.example
-replace (thay cho lệnh cũ taint) = escape hatch của người vận hành: "coi như resource này không tồn tại, tạo lại đi, code không cần đổi". Nó là minh họa: khi đời không theo code, DevOps cần công cụ sửa "đời", nhưng rồi code vẫn là nơi lưu sự thật.

Bài 3.2 — ERR_CONNECTION_REFUSED vs TIMEOUT: mỗi từ là một kết luận điều tra

Browser báoNghĩa làNơi cần soi
refused to connect (ERR_CONNECTION_REFUSED)Gói tin đã xuyên qua SG tới máy — không process nào nghe port, máy tự từ chối✅ firewall ổn → tìm trong máy (service chưa chạy? chưa cài?)
took too long (timed out, ~30s)Gói tin bị chặn ngoài cửa, không tới máy❌ firewall → kiểm ingress, CIDR, network ACL

Bài 3.3 — Đổi user_data trên máy đang chạy = update tại chỗ nhưng script KHÔNG chạy lại

Chuyện: lần apply đầu, plan báo "updated in-place", apply "thành công", nhưng web không lên.
Sự thật: AWS không cho sửa user_data khi máy chạy → provider stop → sửa → start (bằng chứng: public_ip đổi mà id giữ nguyên). Nhưng cloud-init chạy user script với tần suất per-instance — chỉ ở boot ĐẦU TIÊN → máy start lại là boot thứ 2 → script bị bỏ qua.
Học: Terraform nói "apply thành công" ≠ script đã chạy. Bằng chứng là systemctl status nginx → "could not be found". Xác minh sự thật trên máy, không tin lời của công cụ.

Bài 3.4 — Control plane là laptop của bạn

Bạn vô tình gõ terraform plan khi đang SSH trong server → command not found. Đây là minh họa hoàn hảo: Terraform chạy ở máy bạn (nơi có code + state), server chỉ là sản phẩm. Khi quản 50 server, mỗi đầu phiên SSH nên tự hỏi: "mình đang đứng ở máy nào?"

Bài 3.5 — Warning của SSH nói thật đấy

ssh -i ~/ssh/devops-learn (thiếu dấu chấm) → Warning: Identity file ... not accessible nhưng vẫn vào được — vì ssh tự fallback sang key mặc định khác (~/.ssh/id_ed25519...). Cảnh báo không có nghĩa là thất bại, nhưng cũng đừng phớt lờ — hôm nay nó vô hại, hôm sau nó là "key nào đang thực sự mở cửa server này?".

head -20 /var/log/cloud-init-output.log          # bằng chứng script chạy lúc boot
curl -s http://localhost                         # test web NGAY TỪ TRONG máy — tách lỗi service khỏi lỗi mạng
Lệnh cuối là mẹo nghề: nếu curl localhost trong server ra nội dung web mà browser ngoài đời không ra → lỗi nằm ở mạng/firewall giữa đường, không phải ở app. Chia đôi vấn đề để trị.

5 · Quiz tự kiểm tra

1. user_data chạy bằng quyền gì, ở thời điểm nào, do ai thực thi?Root, lúc boot ĐẦU TIÊN của instance, do cloud-init (có sẵn trong AMI) đọc và chạy. Log ở /var/log/cloud-init-output.log.
2. Vì sao đổi user_data mà script không chạy lại?cloud-init chỉ chạy user script ở lần boot đầu; stop/start không phải boot đầu. Terraform vẫn cập nhật thuộc tính (in-place) nên plan "thành công" — nhưng không ai chạy script.
3. user_data_replace_on_change = true có tác dụng khi nào?Với các THAY ĐỔI user_data tiếp theo — chính nó (sự bật flag) không gây replace. Muốn replace ngay: sửa script hoặc dùng terraform apply -replace.
4. Web không lên, browser báo refused — lỗi ở firewall hay trong máy? Vì sao biết?Traffic đã qua được firewall tới máy (refused = máy từ chối vì không có ai nghe). Lỗi ở trong máy (service chưa chạy). Nếu lỗi firewall → timeout.
5. -replace dùng khi nào, nó làm gì?Khi cần tạo lại resource dù code không đổi (đời lệch code). Terraform coi resource như không tồn tại → destroy + create lại.
6. Vì sao ingress 80 mở 0.0.0.0/0 mà ingress 22 mở đúng IP của bạn?Web để phục vụ mọi người; SSH chỉ dành cho bạn — mở cho cả internet = 24/7 bot dò mật khẩu. Least privilege.
