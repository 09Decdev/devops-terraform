Chương 1 · Vòng lặp Terraform & đọc state Học ngày 17/09/2026 — từ file main.tf 12 dòng tới hiểu "Terraform nghĩ gì"

1 · Vòng lặp làm việc với Terraform

terraform init     # 1 lần đầu (+ mỗi lần đổi provider): tải plugin về .terraform/
terraform plan     # tính toán: "nếu apply thì đời sẽ thay đổi gì?" — KHÔNG đụng vào AWS
terraform apply    # làm thật (in plan lần cuối, hỏi "yes")
terraform destroy  # xóa sạch mọi resource Terraform đang quản lý
Tư duy vòng lặp: sửa code → plan → đọc kỹ → apply → plan lần nữa phải ra "No changes". Khi nào plan còn thay đổi là khi đó code chưa phản ánh đúng thực tế.

2 · terraform.tfstate — bộ nhớ của Terraform

State là file JSON ghi: "Terraform đang quản lý resource nào, ID thật của chúng trên AWS là gì, và lần cuối thấy chúng ra sao". 
{
  "version": 4,
  "terraform_version": "1.16.3",
  "serial": 3,                     # số thứ tự bản ghi — mỗi apply là +1
  "lineage": "30cf7503-...",       # mã định danh của file state này
  "resources": [
    {
      "type": "aws_instance",      # kiểu resource
      "name": "example",           # nhãn trong code
      "instances": [
        { "attributes": {
            "id": "i-075ab17e330ceca34",   # ← ID THẬT trên AWS
            "ami": "ami-048cdccbe32bcb9a8",
            "public_ip": "3.25.144.194",
            ...  //  toàn bộ trạng thái AWS trả về
        } }
      ]
    }
  ]
}
Điều cần nhớHậu quả nếu quên
Địa chỉ trong code (aws_instance.example) ↔ ID thật (i-075ab...) chỉ được nối nhau nhờ stateMất state → Terraform không còn biết tài nguyên nào của mình: không update, không destroy được nữa (phải import lại) — và plan sẽ đòi tạo chồng asset mới
State chứa thông tin nhạy cảm (IP, ID, sau này có thể cả secrets)Không commit .tfstate bừa lên Git công khai — chương 6 sẽ học cất nó trên S3

3 · terraform show — đọc state bằng mắt người

terraform show render state thành cú pháp HCL dễ đọc. Khi đọc output dài, phân loại mọi giá trị vào 3 nhóm:
NhómTừ đâu raVí dụ
✍️ Bạn khai báogiống hệt main.tfami, instance_type, tags
🤖 AWS tính toánAWS tự sinh, không ai viếtpublic_ip, private_ip, arn, subnet_id, availability_zone
⚙️ Default providerplugin tự điềntenancy = "default", source_dest_check = true
Và đọc theo cụm chức năng thay vì từng dòng: danh tính (id/arn) → mạng (public/private ip) → đĩa (root_block_device) → bảo mật (metadata_options, key_name) → phần còn lại (cpu_options, enclave_options… bỏ qua được lúc mới học).

4 · Ký hiệu trong plan — bảng tra 4 nút

Ký hiệuNghĩaCâu hỏi cần tự trả lời
+ createtài nguyên mới tinhai tham chiếu nó?
~ update in-placesửa tại chỗ, máy không chếtcó downtime ngầm không?
-/+ destroy and then create replacementđập đi tạo lại — IP mới, ID mới, data trên đĩa mấtdòng nào ghi "# forces replacement"? đó là nguyên nhân thật
- destroyxóa hẳncòn ai tham chiếu nó không?
Kỹ năng lọc nhiễu: khi resource bị replace, cả trăm dòng -> (known after apply) bắn ra chỉ vì AWS chưa tạo lại — đó không phải thay đổi bạn yêu cầu. Lọc hết chúng đi, phần còn lại mới là ý định thật.

5 · Refresh & drift — Terraform kiểm tra thực tế trước khi tin bộ nhớ

Mỗi plan bắt đầu bằng: aws_instance.example: Refreshing state... — Terraform hỏi AWS thật xem mọi thứ còn y hệt như state ghi không. Nếu ai đó lên console xóa/tắt tay một resource (drift), plan sẽ phát hiện và đòi sửa về đúng code. Bài học nghề nghiệp: đừng sửa tay tài nguyên mà Terraform đang quản lý — sửa code rồi apply.

7 · Quiz tự kiểm tra

1. terraform plan có đụng vào hạ tầng thật không?Không — plan chỉ tính toán và in ra. Nhưng nó CÓ gọi API đọc (read-only) để refresh và tra data source.
2. Vì sao "mất tfstate" là tai nạn chứ không phải phiền toái?Mất ánh xạ code↔ID thật → không update/destroy được tài nguyên cũ; apply tiếp sẽ tạo tài nguyên TRÙNG LẶP (cháy tiền double), hoặc phải import lại bằng tay.
3. Dòng nào trong plan cho biết nguyên nhân thật của một replacement?Dòng có # forces replacement bên cạnh thuộc tính bị thay đổi.
4. "known after apply" nghĩa là gì?Giá trị do AWS sinh lúc tạo nên chưa thể biết — hệ quả của việc tạo lại, không phải thay đổi được yêu cầu.
5. Bạn tắt EC2 bằng AWS console, chạy plan — điều gì xảy ra?Refresh phát hiện thực tế lệch state (drift) → plan báo hành động kéo về đúng code (ví dụ start lại máy, hoặc replace). Kết luận: console là chỗ ĐỂ XEM, code mới là chỗ ĐỂ SỬA.
